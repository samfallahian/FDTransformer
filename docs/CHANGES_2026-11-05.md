## Code changes

Every new behaviour has a `Config` switch, so the old recipe can be reproduced exactly:

```
--set LATENT_LOSS_WEIGHT=0 OUTPUT_NORMALIZED=False FP32_OUTPUT_HEAD=False PROMOTE_METRIC=rollout_mse EARLY_STOP_MIN_STEPS=0 VAL_ROLLOUT_SEQS=16
```

Pass `--rollout-seqs 16` too, because the launcher's flag overrides the `Config` value.

### Fix 1: latent-consistency loss (`LATENT_LOSS_WEIGHT = 1.0`)

**Problem.** Every loss scored only the 3 decoded centroid velocities. The decoder's Jacobian from the 47-D latent to those 3 numbers has rank 3, so 44 latent directions got no gradient. The model's predicted latents ended up ~80σ off the data manifold (the checkpoint's validation latent MSE was 2.31, against ~1e-5 for persistence). The rollout feeds those latents back as its own inputs. This is the most likely cause of the ~45–51% ceiling, of the one-step loss to "copy last frame", and of the −3500% first-frame score.

**Change.** New `latent_consistency_loss(pred, tgt, latent_std)` = `mean(((pred − tgt) / latent_std)²)`, where `latent_std` is the model's own per-dim feature std (training split, read from its normaliser buffers after any warm start or resume). It is added with weight `LATENT_LOSS_WEIGHT`:

- to the teacher-forced loss, every micro-batch;
- inside `frame_ar_loss`, on the rolled-out predictions. These are the latents that get fed back, so this is where staying on the manifold matters most. The term is folded into the logged `ar_loss`.

**Monitoring.** The console step line now shows `latent_nmse=`. At startup the trainer logs the copy-previous-frame reference in the same units (about 0.03–0.06). Each eval prints `val latent nMSE=` (wandb `val_tf_latent_nmse`, plus `train/latent_nmse`). A healthy model should land near the reference. The old warm-start checkpoint sits at about 1e4.

**Why weight 1.0.** In standardised units, persistence's latent error is ~0.04 and a good model's centroid L2 is ~0.01, so both terms start at the same order of magnitude. Try `0.1` and `3` if you want to tune it.

### Fix 2: EMA-promoted checkpoints contain the EMA weights

**Problem.** See 1(a). There was also a related bug: on resume, the EMA shadow had been copied *before* the resume load, so it restarted from random weights, and `_latest.pt` didn't store the EMA at all.

**Change.** `save_checkpoint(..., weights_from_ema=True)` is now used for `_rollout_best.pt` and `_best.pt` whenever EMA is on:

- `model_state_dict` and the `_scripted.pt` twin are the EMA weights. These are what warm start and any eval tool load.
- `raw_model_state_dict` holds the live weights.
- `weights_source` is `"ema"` or `"live"`.

`_latest.pt` keeps the live weights (resume needs them) and now also stores `ema_state_dict`. On resume, the EMA shadow is restored from it, or reset to the resumed live weights if it's absent. The eval log line now says "(the EMA weights are what gets saved on promotion)".

### Fix 3: bigger, stratified, per-experiment evaluation with the ridge bar alongside

**Problem.** The headline number came from the first 16 validation rows (~5 per val experiment). There was no per-experiment breakdown, although OVERVIEW §11.3 specified one, and the pooled MSE is dominated by the fastest case (11p4).

**Change.**
- `VAL_ROLLOUT_SEQS = 256` (the launcher default is also 256). Rows come from `stratified_rollout_indices()`: an equal number per `param` value, the first such rows in file order (the HDF5 rows are shuffled at assembly), fixed for the whole run. The startup log prints the split, e.g. `3p6=85 6p4=85 11p4=85`.
- `evaluate()` additionally returns:
  - `improvement_pct/<code>` per experiment, and their unweighted mean `improvement_pct_param_mean`;
  - `ridge_improvement_pct[/<code>]`: the ridge map's own rollout on the **same rows and frames**;
  - `ceiling_captured_pct`: the share of the persistence→ridge gap the model has closed;
  - `val_tf_latent_nmse`.

  A new console line shows them: `[eval] step N: per-param 3p6 +x% (ridge +y%) ... | MEAN ... | ridge mean ... ceiling captured ...`.
- New `PROMOTE_METRIC = 'improvement_param_mean'`. Promotion, and therefore early stopping, now uses the per-experiment mean, which must be > 0 to promote. `'rollout_mse'` restores the old rule.

### Fix 4: `_best.pt` is selected on `val_tf_loss`

It was selected on `val_tf_mse`, the raw latent MSE that fix 1 shows was dominated by untrained directions. It now uses `val_tf_loss`, the quantity actually trained. `best.val_tf_mse` is still tracked for reference.

### Fix 6: early stop never fires before the curricula finish (`EARLY_STOP_MIN_STEPS = None` → auto)

See 1(d). Auto takes the largest of: the LR warmup, the AR-weight ramp, the AR-horizon ramp, and the ridge-distill ramp, counting only those that are active. With the new defaults (20000 steps) that's step 6000. The start-up log prints `[early-stop] patience=5000 steps, not before step 6000`. Set an integer to override, or `0` to disable.

### Fix 7: standardised output head (`OUTPUT_NORMALIZED = True`, `model_variants.py`)

See 1(b). The head now predicts `(latent − feat_mean) / feat_std` (or `delta / feat_std` under `PREDICT_DELTA`), and `forward()` de-normalises it with the model's own buffers. The head then works at unit scale like every other layer, and an optimizer step moves the prediction by a fraction of a latent std rather than many. At initialisation the model predicts the latent mean ± ~0.5σ instead of values ~50× too large.

**Checkpoint compatibility.** No parameter shapes change. Old raw-output checkpoints are converted **exactly** when loaded, by `convert_head_to_normalized()`: `W' = W/s`, `b' = (b − m)/s`. This applies to both warm start and resume. A tested assertion checks that the converted model computes the identical function. On resume of an old `_latest.pt`, the optimizer moments are not reused, because they were accumulated at the old parameter scale.

### Fix 8: output head in fp32 under bf16 autocast (`FP32_OUTPUT_HEAD = True`)

The predicted latent is fed straight back as the next input, so bf16 rounding (~3 significant digits) compounds over 680 sequential tokens. For the old checkpoint, rounding alone moved the decoded centroid by 0.0015 m/s per token, ~20% of the one-step anchor error. The head now runs in fp32 in eager mode and under `torch.compile`. TorchScript exports, which never run under autocast, are unchanged and still verified to round-trip.

### Warm start is opt-in

**Trainer.** `--warm-start` now defaults to `None`, so a cold start (random init) is the default. `--no-warm-start` is still accepted and overrides `--warm-start`. The old built-in default pointed at `saved_models/old/r1_a3b_delta_ar_rollout_best.pt`, which is not in this repo, so a direct `python train_...py --arm X` used to crash at start-up.

**Launcher.**
- Cold start by default.
- `--warm-start` with no argument uses `assets/r2_h11_ridge_distill_rollout_best.pt`; `--warm-start PATH` uses any checkpoint.
- When warm starting, the launcher inserts a **fine-tune schedule** before your `--set` values (so yours win). It's printed in the pre-flight output:
  ```
  AR_FRAMES_START=None AR_WEIGHT_WARMUP_FRAC=0.0 RIDGE_DISTILL_WARMUP_FRAC=0.0 LEARNING_RATE=3e-4 WARMUP_FRAC=0.01
  ```
  This stops the curriculum restart behind 1(c). `--warm-start-keep-schedule` skips it.

### New launcher defaults

| | before | now | why |
|---|---|---|---|
| start | warm (assets ckpt) | **cold** | see the review's "Warm start vs. fresh start" section |
| `--max-steps` | 6000 | 20000 | a cold start needs a real budget; the LR schedule is sized to this |
| `--max-hours` | 3 | 6 | safety net only. Your log showed ~0.3 s/step early on, rising as the AR horizon grows |
| `--val-every` | 250 | 500 | evals are bigger now (256 seqs + EMA + ridge) |
| `--rollout-seqs` | 16 | 256 | fix 3 |
| `--patience` | 1500 | 5000 | scaled to the budget; fix 6 adds the floor |

The trial-112 preset (WD, dropout, EMA 0.98, AR weight) is unchanged. EMA is safe to keep now that fix 2 is in.

## Verification

On CPU in the sandbox, with synthetic 80×10×52 data at the real latent scale and the real frozen decoder:

- **`tests/test_review_fixes.py`** (new, 15 tests, ~1.5 s), plus the existing `test_version_sync.py`: all pass. The new tests cover:
  - the latent loss gives gradient to all 47 dims;
  - head conversion is exact (token and frame models, with and without delta);
  - the head runs in fp32 under autocast;
  - the trace-exported `_scripted.pt` still round-trips and matches eager;
  - stratified indices are balanced and deterministic;
  - `evaluate()` returns per-param and ridge metrics (an identity ridge equals persistence exactly);
  - `frame_ar_loss` includes the latent term;
  - EMA checkpoints store the EMA weights and `_latest.pt` stores live + EMA;
  - the trainer defaults to a cold start.

  `test_data_quality.py` wasn't run because it needs the real data.
- **`--smoke-test`** passes (model builds, causal, trains).
- **`--diagnostics-only`** fits and saves the ridge map.
- **End-to-end training runs:**
  - a cold start with EMA: per-param and ridge lines and the latent nMSE print correctly;
  - a warm start from the asset: the head is converted, the promoted `_rollout_best.pt` / `_best.pt` have `weights_source=ema`, and `_latest.pt` has live weights plus `ema_state_dict`;
  - a resume of that run: the EMA is restored from the checkpoint.
- **Launcher:** `--dry-run` checked for the default, `--warm-start`, `--warm-start PATH --set ...` (the user value wins), `--warm-start-keep-schedule` and `--no-warm-start`.

Not verified here: CUDA-specific paths (bf16 autocast with the fp32 head on a GPU, and `frame_ar` inside the full training loop, which is disabled on CPU), and actual model quality. Both need a GPU run on the real data.

## Suggested next runs

```bash
# GPU 0 -- new default recipe (cold start, all fixes)
./run_train.sh --gpu 0 --round 500 --wandb-group fixes

# GPU 1 -- the §83 question, now on a fair footing
./run_train.sh --gpu 1 --round 501 --wandb-group fixes --set USE_META_COLS=False
```

What to look at, in order:

1. `val latent nMSE` should come down to near the copy-previous-frame reference printed at start-up.
2. `frame1` improvement should stop being hugely negative.
3. The per-param improvements, and `ceiling captured`, show how close you are to the ridge map on the same sequences.
4. The raw and EMA scores should now track each other instead of swinging.

If (1) and (2) improve but the headline doesn't, the next things to try are `--set AR_SEQS=16` (a richer AR gradient) and `--set PREDICT_DELTA=True`.
