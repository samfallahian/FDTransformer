## 1. Predicted latents live far off the data manifold — the most important finding

**What happens.** The only losses are `centroid_velocity_loss` terms: they decode the predicted latent and score the 3 numbers `(vx, vy, vz)` at cube index 62. I measured the decoder Jacobian of those 3 outputs with respect to the 47-D latent at a typical point. It has rank 3 (singular values 1.87, 1.38, 0.98). So locally, **44 of the 47 latent directions get zero gradient** from every loss in the recipe. `PREDICT_DELTA=False` (h11 inherits it from h9) and `AR_DETACH_FEEDBACK=True` leave nothing else that pins those directions down.

**Evidence that it actually happens:**

- The warm-start checkpoint records `best.val_tf_mse = 2.31` on the real validation set. That's the latent-space MSE of its one-step predictions. The real latents have per-dim std 0.010–0.038 and |mean| < 0.008, so persistence's latent MSE is on the order of 1e-5. The model's outputs are off by ~10⁵× that.
- Running the checkpoint on synthetic in-range inputs reproduces this. The predicted latents have |mean| ≈ **1.20** per dim vs the true |mean| < 0.008, and latent MSE = 2.19, which matches the logged 2.31. The output head's row norms (~0.56 on unit-variance LayerNorm features) give the same output scale.
- The decoded centroid is still roughly right (the 3-D projection is trained), so the *metric* looks fine. The other 372 decoded values are not trained at all.

**Why this caps the rollout.** In token tokenization, every predicted token is written back into the context (`rollout_frames`, `frame_ar_loss`). After `NORMALIZE_FEATURES`, an input latent of ~1.2 with `feat_std` ~0.015 sits **~80σ** away from anything seen in teacher-forced training. From the second token of the first rolled-out frame onward, the network conditions on inputs it has never seen. The AR loss is the only thing that teaches it to cope, and it does that on 2 sequences per step (#9). This is a direct mechanism for the "exposure bias" the notebook keeps naming. It also explains why a plain linear map, which is fit on the *full* 470-D latent with MSE and so stays on the manifold, beats every transformer.

**It also cuts against the long-term goal.** A surrogate for the simulation has to produce latents that decode to a sensible 375-D field. Today only the centre point is meaningful.

**Fix (needs a cold start, see the warm-start section):** add a latent-consistency term, e.g. `λ · MSE(normalize(pred), normalize(target))` on the teacher-forced and AR predictions, with λ around 0.1–1 relative to the centroid loss. Alternatively, score the full 375-D decode (Jacobian rank 47, so it constrains every direction). §76's "all125" test isn't a counter-argument: it was a short warm-started fine-tune of a centroid-only checkpoint, scored on 16 sequences. Two complements are worth trying with it. One is `PREDICT_DELTA=True` with the persistence anchor (non-expansive, the v1.0 winner's setting, so the zero-init head starts *at* persistence). The other is predicting in normalized units and de-normalizing with `feat_mean`/`feat_std`.

## 2. "Worse than the previous-frame anchor at every step" was a real signal

§80 found the clean validation teacher-forced loss (0.0086–0.0099) was worse than the copy-previous-frame anchor (0.0074) at 100% of steps, and concluded the check "carried zero information". I disagree. The model has the previous frame in its input. A healthy one-step predictor should at least match copying it, and the ridge map does beat it at one step. Failing to do so is what you'd expect from #1, plus `PREDICT_DELTA=False`: the network has to rebuild the identity from scratch through 6 layers with no residual path to the input latent. The `improvement_pct_frame1 ≈ −1900%` "first-frame anomaly" (§37.1) is the same issue. Within frame 1, tokens 2–10 already condition on the model's own off-manifold outputs. I'd restore the red flag as a health metric, or log `val_tf_loss / anchor` to wandb.

## 3. Two of the three val params are extrapolations — likely the real story behind §83

`prepare_data.py`: train = `4p6, 5p2, 6p6, 7p2, 7p8, 8p4, 10p4` (U = 7.2 … 16.3 m/s). Val = `3p6` (5.6), `6p4` (10.0), `11p4` (17.8). Using the checkpoint's own feature stats (param mean 11.39, std 2.93), the normalized `param` input spans −1.43 … +1.67 in training. In validation it hits **−1.97** and **+2.19**: outside the training range for 2 of the 3 val cases. A model that conditions on `param` is being asked to extrapolate in that input. So "dropping `(x,y,z,t,param)` helps" (§83) is what you'd expect, not a sign of a hidden bug. `t_idx` duplicates the learned time embedding, and its position within a window is arbitrary anyway (windows tile the run at arbitrary phase). `y,z` are constant within a sequence. On top of this, `3p6` was seen by the autoencoder during its own training (§81.2).

**Suggestion:** report per-param results (#5). If `6p4`, the only interpolation case, behaves differently from `3p6`/`11p4`, that settles it. For a fair test of "does param context help", either hold out interpolation params only, or keep `param` and add a train param near each end.

## 4. Bug: EMA-selected checkpoints contain the non-EMA weights

With `EMA_DECAY > 0` (the trial-112 preset sets 0.98), `train()` evaluates both models and then runs `m.update(m_ema)`. The promotion gate, `best`, the early-stop clock and wandb all see the **EMA** numbers. But `save_checkpoint()` writes `model.state_dict()` (the live weights) as `model_state_dict`, and scripts the live model for `_scripted.pt`. EMA weights go only to `ema_state_dict`. So the weights in `_rollout_best.pt`, and anything warm-started from it (`load_warm_start` reads `model_state_dict`), are not the weights that earned the reported number. That covers trial 112's +51.43%, r330/r331, and every run using the default `./run_train.sh` recipe. Fix: when EMA is on, save the EMA state as `model_state_dict` (and script the EMA model) for checkpoints promoted on EMA metrics. Or promote raw and EMA separately.

## 5. The headline metric is measured on 16 sequences

`evaluate()` rolls out the first `VAL_ROLLOUT_SEQS` validation rows. The launcher sets 16. The HDF5 plans are shuffled at assembly, so that's roughly 5 sequences per val param out of ~25k. The rows are fixed, which helps step-to-step comparisons. But a "best" picked as the max over 20+ evals on 5 sequences per condition is biased upward, and differences of 2 points (§83) are well within plausible noise. §11.3's per-param reporting (`metric/3p6`, `metric/6p4`, … and promotion on the mean) was specified but never implemented. **Suggestion:** use ≥256 rollout sequences, stratified by param, with per-param `improvement_pct` and the ridge map's score on the *same* sequences. The rollout is 68 sequential steps however many sequences go in, so the extra cost is mostly batch width, which an H200 has plenty of.

## 6. Warm-start mechanics produce "peak early, then decline" by themselves

On a warm start `step` restarts at 0, so with `--max-steps 6000`:

- The LR re-warms from 0 to **1e-3** over 180 steps, with fresh AdamW moments. The source checkpoint was at 6.9e-4 when saved.
- The AR loss weight restarts at **0** and ramps to 0.683 over 1200 steps (`AR_WEIGHT_WARMUP_FRAC=0.2`).
- The AR horizon restarts at **2 frames** and ramps to 8 over 1800 steps (`AR_FRAMES_START=2`).
- Ridge-distillation weight also restarts its ramp.

So the first ~1000 steps of every warm-started run train mostly teacher-forced, at peak LR, starting from weights that were tuned with the full 8-frame AR loss. A peak around step 250–500 followed by decline is what that schedule does to a model whose rollout skill came from the AR loss. Cold runs also decline later on (§39), so this isn't the whole story, but it does confound every warm-started comparison since §37.

## 7. `_best.pt` is selected on latent MSE

`_best.pt` is promoted on `val_tf_mse`, which #1 shows is dominated by the untrained null-space directions. It should use `val_tf_loss`, the quantity actually trained.

## 8. bf16 rounding of the oversized outputs

Under CUDA autocast the output head emits bf16. At |value| ≈ 1.2 the bf16 spacing is ~0.008, half a true latent std. On the checkpoint, rounding the outputs to bf16 alone moves the decoded centroid by **0.0015 m/s** per token, about 20% of the one-step anchor error (0.0074) and 15× what the same rounding does to true-scale latents. This compounds over the rollout. It mostly disappears once #1 is fixed. Until then, running the output head in fp32 is cheap insurance.

## 9. AR loss signal is very thin

`AR_SEQS=2` on one micro-batch per step, at weight 0.68, with `AR_DETACH_FEEDBACK=True`. Each fed-back token's error, including its 44 off-manifold directions, never receives gradient. That's a likely source of the unexplained pre-clip gradient norms of 10–25× `GRAD_CLIP` (§81.5). §79 showed `AR_SEQS=16` fits. After #1, consider 16–32 sequences and, for short horizons, not detaching the feedback.

## 10. Smaller items

- `MAX_SANE_ROLLOUT_RMSE_MPS = 53.4` m/s, while decoded centroid speeds are ~0.6 m/s. The gate can never fire. Something like 10× the persistence RMS would actually catch divergence.
- One-step ridge distillation (`ridge_distill_targets`, weight 0.5) pulls the prediction toward the ridge map's one-step output. That target is *worse* than the ground truth the teacher-forced loss already uses. At best it's a regulariser. Worth ablating once #1 is fixed.
- The docs reference files that are gone after the cleanup (`singleshot/`, `sweep_deep_dive.py`, most tests). The "242 passing tests" figure in §81.6 no longer applies to this repo, which has 2 test files.
